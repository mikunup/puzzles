01 /

概要

GOAL

［この機能で実現することを1文で言い切ります。例：「確定前の注文なら、受注担当者が画面上で明細の数量・商品を変更できる。」］

背景・解決したい課題

  • ［現状の困りごと・数値］
  • ［要望の出どころ。例：受注チームからの依頼、問い合わせ件数］

範囲

含むもの
［この仕様で作る画面・操作・データ］
含まないもの
［今回は作らないこと。例：確定後の変更、一括変更］
この機能の位置づけ［ドメイン定義書の責務 RESP-001「顧客からの注文を受け付け、内容を確定する」を、受注コンテキストの中で実現する機能の1つです。コンテキスト定義書の「08 機能一覧」にこの仕様書を載せます。］
利用者と利用場面［誰が、いつ、どこで使うかを記載します。例：受注担当者が、顧客からの電話を受けながら、業務システムの注文画面で使う。］

操作の流れ

［利用者の操作を順番に記載します。元になる業務の流れは業務フロー図の作業を参照します。画面の要素や表示は「08 この機能の設計」に書き、ここでは流れと確認ポイントに絞ります。］

  1. ［注文を開く］

    ［注文一覧から対象の注文を選ぶ。状態が「下書き」のときだけ明細を変更できる。］

  2. ［明細を変更する］

    ［数量・商品を変更する。入力のたびに合計金額を再計算して表示する。］

  3. ［保存する］

    ［バリデーションを通れば保存し、変更内容を履歴に記録する。保存後は注文画面に戻る。］

05 /

振る舞いの仕様

［「前提 → 操作 → 結果」の形で、システムの振る舞いを記載します。正常な場合だけでなく、入力の誤り・権限なし・競合などの場合も書きます。この形はテストケースにそのまま展開できます。］

SPEC-0001-01 正常に変更できる

前提
［状態が「下書き」の注文を開いている］
操作
［数量を 1 から 3 に変更して保存する］
結果
［数量 3 で保存され、合計金額が更新される。履歴に変更前後の値が残る］

SPEC-0001-02 確定後は変更できない

前提
［状態が「確定」の注文を開いている］
操作
［明細を変更しようとする］
結果
［明細を変更できない（画面の扱いは 08）。直接 API を呼んでも拒否される］

SPEC-0001-03 価格が変わっていたら確認し直す

前提
［明細を変更する画面を開いた後に、選んだ商品の価格が変更された］
操作
［保存する］
結果
［保存せず、最新の価格と合計金額を表示して確認を求める。確認した後にもう一度保存できる］

SPEC-0001-04 同じ保存は1回だけ反映する

前提
［保存の要求を送った］
操作
［保存を続けて押す。または同じ要求が再送される］
結果
［明細は1回だけ変わり、変更履歴も1件だけ残る。2回目以降は1回目と同じ結果を返す］

状況システムの振る舞い利用者への表示

処理の順序

［画面・API・他のサービスの呼び出しが込み入るときだけ、順番を書きます。業務の流れ（業務フロー図）とは別のものです。図にする場合は、下の手順をシステムシーケンス図に差し替えます。］

  1. ［画面 → updateOrderLines］

    ［明細・注文の版番号・要求 ID を送る。処理中は保存ボタンを押せなくする。］

  2. ［検証する］

    ［権限、注文の状態（下書きか）、版番号、商品の販売状態と価格を確かめる。どれかが合わなければ 409 を返し、何も変えない。］

  3. ［同じ要求か確かめる］

    ［同じ要求 ID がすでに処理済みなら、保存済みの結果を返す。明細も履歴も二重に変えない。］

  4. ［まとめて確定する］

    ［明細の更新、変更履歴の追加、版番号の更新を1つのトランザクションで確定する。どれかが失敗したら全体を確定しない。］

  5. ［他のコンテキストへ知らせる］

    ［確定したあとに、在庫へ「注文明細が変更された」を発行する。］

［応答が途切れた場合、画面は同じ注文の状態を照会してから結果を表示します（05 異常系）。］
