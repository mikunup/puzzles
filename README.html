使い始める

目的に合うHTMLを選んでください。下の資料リンクはすべて別タブで開きます。

業務定義 ↗→業務の流れ ↗→オブジェクト ↗→画面設計 ↗→単体テスト ↗

業務を整理し、必要な情報をまとめ、画面の表示・操作とテストへ具体化します。業務フロー図で作業を整理した後、カレンダーで月・週の完了予定と実績を確認します。計画書はプロジェクト全体の計画に使います。

業務を整理する

業務定義シート ↗

business_definition_sheet.html

業務の目的・担当・入力情報・作業内容・成果物を整理し、業務ごとの定義シートを作成します。

使い方・機能：シートの追加・入力、ブラウザ内保存、JSON読み込み／書き出し、印刷・PDF。

業務フロー図 ↗

business_flow.html

情報項目／ステータスと、みるもの（担当・外部）のマトリクスに作業・帳票を置き、矢印でつないで業務の流れを整理します。

使い方・機能：未配置オブジェクト（作業・帳票）の一括追加、同じIDでの配置・配置解除、別IDへの複製、複数タブで図を編集、Vimキー操作、全画面・集中表示、元に戻す／やり直す、ブラウザ内保存、JSON読み込み、全タブJSON保存・復元、JSON／Markdown／HTML書き出し（行・列の意味を含む）、印刷・PDF。

オブジェクト整理 ↗

object_model.html

オブジェクトの名前・プロパティ・操作を整理し、シングルとコレクションの表示項目・操作を設計します。

使い方・機能：複数タブ、Vimキー操作、全画面・集中表示、Enum型の保存値・表示名・初期値設定、オブジェクト・コレクションの編集、参照関係図・マトリクス・関係一覧、ブラウザ内保存、JSON読み込み／書き出し・全タブ保存。

業務タスクの完了予定（カレンダー） ↗

calenderschedule.html

業務フロー図で整理した作業に日付を割り当て、月・週ごとにいつ完了するかを可視化します。作業名・担当・前工程を手動で登録し、開始日と完了予定日を設定します。参考月の業務フローを見るために使い、件数の集計や現在日による超過判定は表示しません。

使い方・機能：月／週表示、完了予定日順の一覧、未着手／作業中／完了・実際の完了日、ガント・担当別表示、Vim操作、集中・全画面、補助パネル開閉、ブラウザ内保存。既存データは引き継ぎ、状態がない予定は未着手として扱います。

ドメインからシステムを設計する

業務の整理から一歩進めて、システムが担う責務を決め、サブドメインごとに分けて解決し、機能に落とし込むための資料です。最初に使い方を読み、上から順に書きます。

  1. 使い方を読む：3つの雛形の関係と、コンテキストの分け方を確認します。
  2. ドメイン定義書（システムで1つ）：システムがまたがるドメインとサブドメイン、システムの責務（RESP）を洗い出し、解決するコンテキストを決めます。
  3. コンテキスト定義書（コンテキストごとに1つ）：担う責務を、用語・モデル・ルール・状態で解決し、作る機能を一覧にします。
  4. 機能仕様書（機能ごとに1つ）：責務を実現する機能を1つずつ定義し、画面・機能設計書と画面単体テストケースへ展開します。

3つの雛形の使い方（最初に読む） ↗

howtocontext.html

雛形ではなく、ドメイン定義書・コンテキスト定義書・機能仕様書をどうつなげて書くかを説明する資料です。この資料で何かを作るのではなく、3つの雛形を書き始める前に読みます。

内容：Domain → Context → Model（業務フロー・オブジェクト）→ Spec → Catalog と Design の関係図・ディレクトリ構成、責務（RESP）のたどり方、コンテキストの分け方（1対1・分割・統合の判断）、業務モデル（Model）・実体の一覧（Catalog）・共通ルール（Design）へのつなぎ方、どこに何を書くか、作る順番、用語の揃え方、更新のルール。

ドメイン定義書の雛形 ↗

domain.html

システムで1つ作成し、システムがまたがるドメインとサブドメイン、システムが実施する責務、解決するコンテキストとの対応（1対1・分割・統合）と関係を整理します。

使い方・機能：システムで1ファイル作成します。ドメイン一覧、システムの責務（RESP）表、サブドメイン一覧（ドメイン別・コア・支援・汎用）、コンテキストとの対応表（1対1でない理由・ADR）、関係一覧と関係パターンの意味、境界をまたぐ用語、課題表付き。

コンテキスト定義書の雛形 ↗

context.html

責務を分けたサブドメイン1つを解決する領域として、担う責務・用語・モデル・ルール・状態・イベント・連携・機能一覧を記録します。

使い方・機能：サブドメインにつき1ファイル複製し、［ ］内を書き換えて使います。担う責務表、用語集、概念一覧（集約・エンティティ・値オブジェクト）、ルール表、状態遷移表、イベント表、連携表、機能一覧（仕様書と責務の対応）付き。

機能仕様書の雛形 ↗

specs.html

1つの機能について、目的・要件・操作の流れ・振る舞い・データ・受け入れ基準（What）と、この機能の設計（画面・API・テーブル）を記録します。

使い方・機能：1つの機能につき1ファイル複製し、［ ］内を書き換えて使います。属するコンテキストと実現する責務（RESP）、ステータス（下書き・レビュー中・確定・取り下げ）、優先度付き要件表、前提→操作→結果のケース、入力バリデーション表、受け入れ基準表、この機能の設計（画面・API・データベース・共通ルールからの例外）付き。仕様と設計のステータスは別に管理します。

画面を設計・テストする

画面・機能設計書 ↗

使い方・機能：設計例を参照し、HTML内の内容を編集して自分のシステムの設計書に使います。見本の購入・保存は実行しません。

画面グループごとに「目的 → 前提 → ケース表」を読み、正常・バリデーション・異常を確認します。

使い方・機能：OK／NG・保留の記録、実績メモ、集計、ブラウザ内保存、結果のJSON書き出し。自動テストの実行ページではありません。

共通デザインの適用

全18ページは、各HTMLファイル1つで表示・操作できる構成です。CSS・JavaScript・表示に必要な画像はHTML内に含め、外部の共通CSSなどには依存しません。配色・フォーカス表示・タブの選択表示はbases/の基準に合わせています。実装ルールはbases/display.htmlを参照してください。資料間のリンクや、利用者が選んで読み込むJSONは別ファイルとして扱います。

共通スタイルの編集元はbases/base.cssです。リポジトリ直下でpython3 bases/sync_styles.pyを実行すると、全HTMLの埋め込みCSSを直接更新できます。保存時の自動反映はpython3 bases/sync_styles.py --watch（Ctrl+Cで終了）、反映漏れの確認はpython3 bases/sync_styles.py --checkを使います。確認モードは未反映があると終了コード1を返します。

共通CSSの範囲（<!-- bases:styles:start -->〜<!-- bases:styles:end -->）は同期で上書きされます。共通変更はbase.cssを編集し、ページ固有のCSSは範囲外に記述してください。新規HTMLにも開始・終了マーカーを1組配置してください。

  • 編集画面：業務フロー図・カレンダー・オブジェクト整理・アウトラインは全幅の作業領域を使います。業務定義シート・スケジュール計画書も画面幅を活かして表示します。
  • 資料画面：資料一覧・説明資料の雛形・ADR・ドメイン定義書・コンテキスト定義書・機能仕様書の雛形とその使い方・画面設計書・画面単体テストは、本文の領域を最大1440pxのレイアウト内で広く確保し、狭い画面では目次と本文を縦に並べます。
  • タブ操作：タブにフォーカスした状態で左右矢印・Home・Endを使えます。業務定義シートはシート、カレンダーは表示方法、業務フロー図・オブジェクト整理・アウトラインは作業を切り替えます。
  • Vim操作・集中表示・全画面：業務フロー図・カレンダー・オブジェクト整理・アウトラインで利用できます。キーの意味は各ページの操作ヘルプを確認してください。アウトラインのパネル開閉はパネル見出し（OUTLINE / 見取り図）の横から操作できます。
  • 印刷：画面用の幅変更は印刷に適用せず、各ページの印刷用レイアウトを使用します。

編集と保存

  • 編集ツールのページ：業務定義シート・業務フロー図・オブジェクト整理・カレンダー・アウトラインは、画面内で内容を入力します。
  • 資料のページ：画面設計書・スケジュール計画書・説明資料・ADR・ドメイン定義書・コンテキスト定義書・機能仕様書の雛形は、HTML内の文章や表を書き換えて使います。
  • テストの記録：画面単体テストケースは、画面内で実施結果とメモを入力できます。
  • ブラウザ内の保存：データは端末間で自動共有されず、HTMLファイル自体にも書き戻されません。別のブラウザや保存場所では同じ記録を参照できない場合があります。
  • 書き出し：JSON機能があるページでは、受け渡しや控えに書き出しを使います。読み込み機能の有無は各ページのボタンを確認してください。

ローカルデータの管理

  • datas/：ローカルにダウンロードしたJSONや、各ツールから書き出したデータなどを追加して保存・管理するディレクトリです。必要に応じて、各ページのJSON読み込み機能で利用します。
  • .gitignore：Gitの管理対象から除外するパスを指定するファイルです。/datas/を指定し、このリポジトリ直下のdatas/とその配下のファイル・サブディレクトリを除外しています。
  • datas/内のデータはコミット・共有されません。新しくクローンした環境では、必要に応じてdatas/を作成し、データを配置してください。README.mdのdatas/へのリンクは、対応するファイルをローカルに配置した場合に利用できます。
