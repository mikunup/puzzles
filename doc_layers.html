HOW TO USE THE DOCUMENT LAYERS

資料の層と使い方

3つの雛形を軸に、Domain → Context → Model → Spec → Catalog と粒度を下げながら、システムを形にしていきます。ドメイン定義書でシステムがまたがるドメイン・サブドメインと責務を洗い出し、コンテキスト定義書で責務をサブドメインごとに分けて解決します。業務の流れ（Flows）と扱う「もの」（Objects）は、システムで1つにまとめた業務モデルに描き、機能仕様書で責務を実現する機能を1つずつ、その機能の作り方まで含めて定義します。仕様書で決めた画面・API・テーブルの実体は Catalog に集め、全機能に共通するルール（非機能要件の満たし方・共通ルール）は Design にまとめます。

対象
設計資料を書く人・読む人
雛形
domain.html / context.html / specs.html
業務モデル
business_flow.html / object_model.html（05）
設計
機能ごとは仕様書 08、実体は Catalog、ルールは Design（06）
01 /

資料の役割と層

資料は層に分かれ、層ごとに扱う範囲（単位）と答える問いが違います。1つの資料に全部を書かず、層ごとに分けるのが基本です。

層・資料1ファイルの単位答える問い主な読者作るタイミング
Domainドメイン定義書
domain.html		システムで1つこのシステムは、どのドメイン・サブドメインにまたがり、どんな責務を担うか。責務をどのコンテキストで解決し、コンテキスト同士はどう関係するか事業・業務の責任者、全チームのリーダー、アーキテクト最初に1回。責務や分け方が変わったら更新
Contextコンテキスト定義書
context.html		サブドメインごとに1つこのサブドメインを解決する領域では、どの責務を、どんな言葉・モデル・ルール・状態で実現するか。どの機能を作るかそのサブドメインの業務担当者と開発チームサブドメインが決まったら。用語・ルール・機能が増えたら更新
Model業務モデル
業務フロー図（Flows）
オブジェクト整理（Objects）		システムで1つ
Flows・Objects とも1ファイル。Flows はタブで分ける		各コンテキストで、誰が、どの順に、どの作業・帳票で業務を進めるか。コンテキストをまたぐと全体はどう流れるか（Flows）。システムでどんな「もの」を扱い、それぞれが何を持ち、何ができるか（Objects）そのコンテキストの業務担当者と開発チームコンテキスト定義書の用語・状態が見えてきたら。業務の流れや項目が変わったら更新
Spec機能仕様書
specs.html		機能ごとに1つこの機能で、誰が、何をできるようになるか。どう振る舞えば責務を果たしたと言えるか（01〜07）。この機能をどう作るか。使う画面・API・テーブル（08）01〜07 は業務担当・開発・テスト担当、08 は開発者機能を作る前。01〜07 の確定後は変更履歴に残す。08 は開発しながら更新
Catalog実体の一覧
画面・API・テーブル		システムで1つシステムに今どんな画面・API・テーブルがあり、それぞれがどう定義されているか（実体）開発者・テスト担当仕様書の 08 を書いたら、追加・変更を反映する
Designシステム共通のルール
非機能要件・共通ルール		システムで1つ全機能に共通して、どう作るか。非機能要件をどう満たすか。Frontend・IF・DB・Infra の共通ルール開発者・アーキテクト・運用担当最初の仕様書の前に粗く作り、開発しながら育てる
ドメインは「問題」、コンテキストは「解決」ドメイン定義書はシステムで1つ作り、システムがまたがるドメインと、その中で解く問題（サブドメイン・責務）を書く資料です。含む順は システム ⊃ ドメイン ⊃ サブドメイン で、1つのシステムが複数のドメインにまたがることもあります。コンテキスト定義書は、1つのサブドメインをシステムでどう解決するか（用語・モデル・ルール）を書く資料です。基本は「1つのサブドメイン ＝ 1つのコンテキスト」で対応させます。分割・統合してよい場合は「04 コンテキストの分け方」を参照してください。
What と How の分かれ目Domain・Context・Model は、業務を理解して整理する工程（業務モデリング）です。仕様書の 01〜07 でシステムに求めることを確定します。ここまでには、実装の技術を変えても変わらないこと（What）を書きます。「どう作るか」（How）は、機能ごとのことを仕様書の 08 に書き、その結果の画面・API・テーブルの実体を Catalog に集めます。全機能に共通するルールは Design に書きます。
02 /

関係の全体図

上から下へ枝分かれします。ドメイン定義書はシステムで1つで、サブドメイン1つに、基本はコンテキスト定義書が1つ対応します（分割・統合する場合は 04 を参照）。業務モデルはシステムで1つにまとめ、Flows も Objects も1つのファイルにします。Flows はコンテキストごとのタブに分けて描きます。そこから作る機能ごとに仕様書ができます。仕様書には、その機能の作り方（08）まで書きます。08 で使う・足す・変える画面・API・テーブルは、システムで1つの Catalog（実体）に反映します。最下段の Design（ルール）には、仕様書の 08 と Catalog が従う共通ルールを置きます。

上から下へ：責務を分ける

ドメイン定義書で責務を洗い出して割り当て、コンテキスト定義書でそのサブドメインの解決のしかたを決めます。業務モデルで業務の流れと扱う「もの」を具体化し、仕様書で責務を実現する機能を1つずつ、作り方まで定義し、その実体を Catalog に反映します。作り方は Design の共通ルールに従います。

下から上へ：ずれを戻す

業務フローを描いていて「この作業を担う責務がない」、仕様書を書いていて「この用語はコンテキスト定義書にない」と気づいたら、上の資料を直します。設計の途中で「この仕様は技術の制約で満たせない」と気づいたときも同じです。下の資料だけで辻褄を合わせないのが大切です。

横から：ADR で理由を残す

責務をどのサブドメインに入れたか、連携を API にしたかイベントにしたか、どの技術を採用したか、といった判断は ADR に記録します。各資料には結果だけを書き、理由は ADR へのリンクにします。

ディレクトリで見た全体

同じ関係を、資料を置くフォルダの構成で表すと次のようになります。Spec はコンテキストのフォルダの中に、Domain・Model・Catalog・Design・ADR はコンテキストの外（システムで1つ）に置きます。実体（Catalog）とルール（Design）は別のフォルダに分けます。Flows はシステムで1つのファイルにし、コンテキストごとのタブに分けて描きます。

03 /

責務でつなぐ

各層の資料は、責務の ID（RESP-xxx）でつながります。1つの責務が、どの資料のどこに現れるかを例で示します。仕様書は「コンテキストの中で、責務を実現する機能」として定義します。

  1. ドメイン定義書 03 システムの責務：責務を定義する

    RESP-001「顧客からの注文を受け付け、内容を確定する」。きっかけは「顧客が注文を送信する」、結果は「確定した注文」。

  2. ドメイン定義書 04 サブドメインとコンテキスト：担うサブドメインと、解決するコンテキストを決める

    RESP-001 は「販売」ドメインの「受注」サブドメインが担い、1対1で「受注」コンテキストが解決する。受注のコンテキスト定義書は context-order.html。

  3. コンテキスト定義書（受注）01 解決する領域：責務を引き受ける

    「担う責務」の表に RESP-001 を載せ、このコンテキストでの実現のしかた（注文集約を作り、確定時に RULE-001 を検査する）を書く。

  4. 業務モデル（Flows の受注タブ・Objects）：責務を業務の流れと「もの」に落とす

    業務フロー図の「受注」タブで RESP-001 を「顧客が注文を送信 → 受注担当が明細を確認・変更 → 注文を確定」と描く。システムで行う作業「明細を変更する」「注文を確定する」が機能の候補になる。システムで1つのオブジェクト整理に、「注文」「注文明細」のプロパティと操作を書く。

  5. コンテキスト定義書（受注）08 機能一覧：機能に分ける

    RESP-001 を実現する機能として、SPEC-0001「注文明細を変更する」と SPEC-0002「注文を確定する」を載せる。

  6. 機能仕様書（SPEC-0001）：機能を定義する

    見出しの「コンテキスト」に受注、「実現する責務」に RESP-001 を書く。要件の根拠には、受注コンテキストのルール（RULE-002）を挙げる。08 この機能の設計には、使う画面「注文詳細」、提供する API updateOrderLines、書き込むテーブル order_lines を書き、Catalog の実体へリンクする。

抜け漏れの確認ドメイン定義書のすべての RESP が、どれか1つのコンテキストの「担う責務」に載っていること。コンテキストのすべての RESP が、「機能一覧」のどれかの仕様書で実現されていること。業務フローのうちシステムで行う作業が、どれかの機能に対応していること。この3つを確認すると、作り忘れと、担当のはっきりしない機能を防げます。
04 /

コンテキストの分け方

基本は「1つのサブドメイン ＝ 1つのコンテキスト」です。サブドメインは事業として解く「問題」の分け方で、こちらで選べるものではありません。コンテキストは「解決」の分け方で、言葉・チーム・技術・整合性の都合で設計するものです。1対1から外れてよいのは、解決の側にはっきりした理由があるときだけです。

パターン1：1つのサブドメインを、複数のコンテキストに分割する

分割するサイン例分け方
同じサブドメインの中で、言葉の意味が変わる
最も強い理由		在庫サブドメインで、倉庫の「在庫」はロット・棚番を持つ物理的なもの、販売の「在庫」は引き当て可能な数倉庫在庫と販売可能在庫のコンテキストに分ける
1チームで持てない大きさ受注が大きくなり、1チームで用語・ルールを把握しきれないチーム単位で分ける。1コンテキスト＝1チームが目安
変更頻度・リリースの周期が大きく違う料金計算は週に何度も変わるが、注文の確定処理はほとんど変わらない頻繁に変わる部分を切り出す
非機能要件が大きく違う決済のカード情報だけに PCI DSS の厳しい管理が要る。セール時に商品の閲覧だけが高負荷になる規制・性能の対象の部分を隔離する
整合性の要求が違う在庫の引き当ては即時に正しい必要があるが、売上の集計は数分遅れてもよい強い整合性が要る部分と、結果整合でよい部分を分ける
一部を既製品・レガシーが担う請求のうち、請求書の発行だけを外部サービスに任せる外部の部分を別のコンテキストとして扱い、腐敗防止層をはさむ
書き込みと読み取りで、モデルが大きく違う業務の処理と、経営向けのレポート・検索参照専用のコンテキストを作る

パターン2：複数のサブドメインを、1つのコンテキストに統合する

統合するサイン例
初期で小規模、チームが1つ立ち上げ期で、受注と在庫を1チームが作っている。境界がまだ確かでないなら、早すぎる分割は避ける
いつも一緒に変わる機能を足すたびに、2つのサブドメインを必ず同時に直している
同じトランザクションで強い整合性が要る請求と入金の消し込みを、必ず同時に成功・失敗させる必要がある
汎用サブドメインを1つの製品でまかなう会計と経費精算を、1つの SaaS がまとめて担う
実は言葉の意味が同じ分けてみたら用語がほぼ共通で、変換のコストばかり増える
統合するときの注意統合は、同じドメインのサブドメイン同士に限るのが原則です。違うドメインのサブドメインをまとめると、用語・ルールを決める業務の責任者が2人になり、変更のたびに調整が必要になります。また、コンテキストを1つにまとめても、コードのモジュール・パッケージはサブドメインごとに分けておきます。チームが増えたときや、変更の周期がずれてきたときに、切り出しやすくなります。

やってはいけない分け方

エンティティ（CRUD）単位

「顧客サービス」「商品サービス」のような分け方。ルールが散らばり、どの操作も複数のサービスを呼ぶことになります。

技術のレイヤー単位

画面・API・データベースで分けても、言葉の境界にはなりません。

画面単位

画面は Catalog で管理する実体で、複数の機能から使われます。コンテキストの単位ではありません。

組織図だけ

言葉もモデルも同じなのに、部署が違うという理由だけで分けることです。

分け方が間違っているサイン

分けすぎのサインまとめすぎのサイン
1つの機能追加で、いつも2つのコンテキストを同時に直す用語の定義に「〜の場合は」という条件が増える
同期 API の呼び出しが、鎖のように連なる同じ概念に、場面ごとの分岐やフラグが増え続ける
分散トランザクションや、データベースの共有が必要になる複数のチームが、同じコードで頻繁にぶつかる
連携のための変換コードが、業務ロジックより多い1つの集約・モデルが巨大になり、誰も全体を説明できない

判断の順番

  1. まず1対1で置く

    ドメイン定義書 04 の「コンテキストとの対応」に、サブドメインと同じ名前のコンテキストを1つずつ置きます。

  2. 言葉の意味が割れていないかを見る

    1つのサブドメインの中で、同じ言葉が場面によって違う意味になっていれば分割します。これが最も強い理由です。

  3. チーム・変更頻度・非機能要件・整合性を見る

    1つのサブドメインの中で、これらが大きく違えば分割を検討します。

  4. まとめるべきものを見る

    いつも一緒に変わる、または強い整合性が要るサブドメイン同士は、統合を検討します。

  5. 1対1でないものは ADR に残す

    理由を ADR に書き、ドメイン定義書 04 の「1対1にしない理由」「ADR」列を埋めます。チーム構成や規模などの前提が変わったら見直します。

05 /

Model：業務フローとオブジェクト

業務モデル（Model）は、業務を具体的に描く層です。開発に入る前に、業務の流れ（Flows）と、業務で扱う「もの」（Objects）を、業務担当者と一緒に整理します。どちらもシステムで1つのファイルにまとめて管理します。Flows はコンテキストごとのタブに分けて描き、Objects はタブを分けずにシステム全体で1つにします。ここで描いた作業と項目が、仕様書（01〜07 と 08 この機能の設計）の元になります。

業務モデル単位答える問い書くこと次につながる先
Flows業務フロー
業務フロー図		システムで1つ。タブ＝コンテキスト ＋「全体」誰が、どの順に、どの作業・帳票で業務を進めるか行に情報項目・ステータス、列にみるもの（担当・外部）を置き、マスに作業と帳票を並べ、矢印で流れと情報の受け渡しをつなぐシステムで行う作業 → コンテキスト定義書 08 機能一覧・仕様書 04 操作の流れ
Objectsオブジェクト
オブジェクト整理		システムで1つどんな「もの」を扱い、何を持ち、何ができるかオブジェクトごとのプロパティ・型・候補値（Enum）・操作、コレクション（一覧）の表示項目と操作、参照関係仕様書 06 データ項目、仕様書 08 の画面（オブジェクト → 詳細、コレクション → 一覧）・API の型・テーブル

コンテキスト定義書との役割分担

コンテキスト定義書の 03 ドメインモデルと 05 状態とライフサイクルは要約として残し、詳しい内容は業務モデルに書きます。同じことを2か所に書かないためです。

内容コンテキスト定義書（要約）業務モデル（詳細）
扱う「もの」03 ドメインモデル：概念の名前、集約・エンティティ・値オブジェクトの区分、集約の境界Objects：プロパティ・型・候補値・操作、コレクション、参照関係
状態と業務の流れ05 状態とライフサイクル：状態の一覧と、どの状態からどの状態へ移れるかFlows：その遷移を、誰が、どの作業・帳票で起こすか。行のステータスは 05 の状態名をそのまま使う

コンテキストをまたぐ流れは「全体」タブへ

「受注 → 在庫の引き当て → 請求」のように複数のコンテキストをまたぐ業務の流れは、業務フロー図に「全体」タブを作って描き、ドメイン定義書 05 コンテキスト間の関係からリンクします。各コンテキストのタブは、その中の自分の部分を詳しく描きます。境界をまたぐ受け渡しは、コンテキスト定義書 06 イベント・07 連携に現れます。

Objects をシステムで1つにするときの注意

同じ名前でもコンテキストによって意味が違うもの（受注の「商品」＝販売単位、在庫の「商品」＝保管単位）は、別のオブジェクトにして名前にコンテキストを添えます（例：商品［受注］・商品［在庫］）。説明欄には意味を書き写さず、コンテキスト定義書 02 の用語へのリンクを書きます。意味の正本は 02 です。1つにまとめると、コンテキストをまたぐ参照関係が1か所で見えます。

Flows → Objects の順に描く

先に業務フロー図で作業と帳票を並べると、帳票や情報項目から扱う「もの」が見つかります。それをオブジェクト整理でオブジェクトにし、プロパティと操作を書き出します。名前はコンテキスト定義書 02 ユビキタス言語に揃え、新しい言葉が出てきたら 02 に追加します。

DDD での呼び方Model の層は、DDD のドメインモデリングに当たります。Flows はドメインストーリーテリング（アクター・ワークオブジェクト・アクティビティ）や Event Storming のプロセスモデリングに近く、Objects のプロパティ・操作はエンティティ・値オブジェクトの詳細です。コレクション（一覧）は、DDD ではなく OOUI（オブジェクト指向 UI）の考え方です。

Catalog と Design：実体とルール

「どう作るか（How）」は3か所に分けて書きます。1つの機能の作り方は、その機能の仕様書の「08 この機能の設計」に書きます。その結果できる画面・API・テーブルの実体は、システムで1つの Catalog に集めます。全機能に共通するルール（非機能要件の満たし方・共通ルール）は、システムで1つの Design に書きます。Catalog は「今あるもの」、Design は「どう作るかの決まり」です。

バリデーションの置き場所

「バリデーション」には性質の違うものが混ざっています。次の順に判断すると、置き場所が1つに決まります。

  1. 業務担当者が「決まりだ」と説明できるか

    はいなら、コンテキスト定義書 04 の RULE に書きます。例：数量は 1〜999、確定後は変更できない。

  2. データの形の話か

    型・候補値なら Objects、要求の形式や上限なら Catalog の API 定義に書きます。

  3. この機能の画面での扱いか

    必須・任意や、エラー時の表示文言なら、仕様書 05 に書きます。

  4. 全画面・全 API で同じか

    エラーの出し方や認証なら、Design の共通ルールに書きます。

コンテキスト定義書 04  RULE-004：注文明細の数量は 1 以上 999 以下とする（根拠：受注業務規程）
Objects               注文明細［受注］.quantity：整数（範囲は RULE-004）
仕様書 05             数量 ｜ 必須 ｜ RULE-004 ｜「数量は 1〜999 で入力してください」
Catalog API 定義      quantity: integer, minimum 1, maximum 999（RULE-004 を実装）
Design                エラーは項目の直下に文字で表示する（全画面共通）

例：ルールを変えるときは RULE-004 を直し、RULE-004 を参照している場所を見直します。

08 /

作る順番

新しいシステムなら Domain → Context → Model → Spec の順に書き、最初の仕様書の前に Design の土台を粗く作ります。既存システムに機能を足すなら、該当するコンテキストの業務モデルと仕様書から始めて、必要なところだけ上の資料と Design を直します。

新しいシステムを設計するとき

  1. ドメイン定義書でドメインと責務を洗い出す

    システムにつき domain.html を1つ作り、01 概要、02 ドメイン一覧、03 システムの責務を書きます。先に、システムがまたがるドメインと業務の責任者を確認します。責務は、人が行う業務と分けて書きます。

  2. ドメインをサブドメインに分け、コンテキストを決める

    04 で、各ドメインをサブドメインに分けて責務を割り当て、まず1対1でコンテキストを置きます。そのうえで「04 コンテキストの分け方」のルールで、分割・統合が必要かを確認します。ドメイン定義書 05 で関係を粗く描き、業務フロー図の「全体」タブに、コンテキストをまたぐ業務の流れを粗く描きます。

  3. サブドメインごとにコンテキスト定義書を作る

    context.html を、サブドメイン1つにつき1ファイル複製します。01 で担う責務を引き受け、業務担当者と一緒に 02 用語・04 ルールを書き、03 モデル・05 状態は要約を書きます。

  4. 業務モデルを描く（Flows → Objects）

    業務フロー図にコンテキストごとのタブを作り、コンテキスト定義書 05 の状態を行にして、誰がどの作業・帳票で状態を進めるかを整理します。帳票や情報項目から、システムで1つのオブジェクト整理にプロパティ・操作・コレクションを書きます（05）。新しい用語・状態が出てきたら、コンテキスト定義書に戻して追記します。

  5. 分け方や連携の判断を ADR に残す

    「なぜこの責務をこのサブドメインに入れたか」「なぜイベント連携にしたか」を adr.html に記録し、該当箇所からリンクします。

  6. Design の土台を作る

    最初の仕様書を書く前に、非機能要件の目標と満たし方、Frontend・IF・DB・Infra の共通ルールを粗く書きます（06）。技術選定の理由は ADR に残します。土台は開発しながら育てます。

  7. 機能一覧を作り、仕様書の 01〜07 を書く

    業務フローのうちシステムで行う作業を、コンテキスト定義書の 08 機能一覧に並べ、specs.html を機能につき1ファイル複製します。見出しにコンテキストと実現する責務を、関連資料に元になった業務モデルを書きます。業務担当とレビューして確定します。

  8. 仕様書の 08 にこの機能の設計を書く

    仕様書の 04・05 と Objects から使う画面と画面要素を、06 とコンテキスト定義書 07 から API の入出力を、Objects と 03 の集約の境界から読み書きするテーブルを書きます。新しく作る画面・API・テーブルは、Catalog にも追加します。

  9. テストへ展開する

    仕様書の 05 振る舞いと 07 受け入れ基準を画面単体テストケースに展開し、設計どおりに作ったものが受け入れ基準を満たすかを確認します。

既存のシステムに機能を足すとき

  1. どのコンテキストのどの責務か決める

    足したい機能が、どのコンテキストのどの RESP を実現するかを決めます。当てはまる責務がなければ、ドメイン定義書 03 に責務を追加し、04 で担うサブドメインと解決するコンテキストを決めます。

  2. 業務モデルを直す

    業務フロー図の、そのコンテキストのタブに作業を足し、必要ならオブジェクト整理にプロパティ・操作を足します。コンテキストをまたぐ流れが変わるなら、「全体」タブも直します。

  3. 仕様書を書き、機能一覧に載せる

    specs.html を書き、コンテキスト定義書の 08 機能一覧に追加します。新しい用語・ルール・状態が出てきたら、コンテキスト定義書の該当箇所に追記します。

  4. この機能の設計を書き、Catalog を直す

    仕様書の 08 に使う画面・API・テーブルを書き、Catalog（画面・API・テーブルの実体）に追加・変更を反映します。共通ルールで足りないときは、例外として 08 に書き、理由を ADR に残します。

用語を揃える流れ

責務と並んで、各層の資料をつなぐのが用語です。「商品」という言葉を例に、どの資料にどう現れるかを示します。

資料書き方の例役割
ドメイン定義書
06 境界をまたぐ用語		商品 ／ 受注 02・在庫 02・請求 02 で意味が違う ／ 受注 → 在庫は SKU からロットへ変換同じ言葉がコンテキストをまたぐと意味が変わることと、連携時の変換を示す。意味そのものは書き写さない
コンテキスト定義書（受注）
02 ユビキタス言語		商品 ／ Product ／ 顧客が注文できる販売単位。SKU で識別する ／ 「品目」とは呼ばないそのコンテキストでの定義を1か所に置く。コード・画面・会話で同じ名前を使う
業務モデル
Flows・Objects		業務フロー図「受注」タブの帳票「注文書」の明細に「商品」。オブジェクト「商品［受注］」のプロパティ sku業務の流れとオブジェクトでも、ユビキタス言語の名前をそのまま使う
機能仕様書（明細の変更）
02 用語・前提		商品 ／ 定義：コンテキスト定義書（受注）02 ／ 補足：なし定義を書き写さず参照する。入力項目の名前は Product・sku に揃える
仕様書 08・Catalog画面のラベル「商品」、API の項目 sku、テーブルの列 order_lines.sku設計の都合で別の名前を作らない
ID で結びつけるドメイン定義書の責務は RESP-001・課題は SYS-001、コンテキスト定義書のルールは RULE-001、仕様書は SPEC-0001・要件は REQ-001・受け入れ基準は AC-001 のように番号を付けると、資料をまたいで「どれの話か」を指せます。

更新のルール

1つの資料を変えたら、つながっている資料のどこを見直すかを決めておきます。

変えたこと見直す資料記録する場所
ドメインを追加した（システムの範囲が広がった）ドメイン定義書 02 にドメインを、04 にサブドメインとコンテキストを追加する。05 でドメインをまたぐ連携を、業務フロー図の「全体」タブで流れを確認するドメイン定義書の変更履歴。範囲の判断は ADR
責務を追加・削除した担うコンテキスト定義書の 01 担う責務と 08 機能一覧、業務モデル。削除なら、その責務を実現していた仕様書ドメイン定義書の変更履歴
責務を別のサブドメインに移した移す前と後のコンテキスト定義書の 01・08 と業務モデル。関係する仕様書の「コンテキスト」と 02 用語・06 データの参照先ADR に決定を残し、ドメイン定義書の版数を上げる
コンテキストを分割・統合したドメイン定義書 04 の対応表。コンテキスト定義書を分割・統合し、01 担う責務・08 機能一覧を振り分ける。業務フロー図のタブと、オブジェクトの所属（名前に添えたコンテキスト）を振り分ける。関係する仕様書の「コンテキスト」を直すADR、ドメイン定義書の変更履歴
チーム構成・規模が変わった1対1でない対応の ADR を読み直し、分割・統合の理由がまだ成り立つかを確認する見直した結果を ADR に追記する。変える場合は新しい ADR
連携方式を変えた（API → イベントなど）ドメイン定義書 05、両側のコンテキスト定義書 07、利用側の仕様書 06・08、Catalog の API 定義ADR
用語の定義・ルール（バリデーションを含む）・状態を変えたその RULE 番号を参照している Objects の説明・仕様書 05・Catalog の API 定義。その用語・ルール・状態を使う業務モデル（業務フロー図の行、オブジェクト整理の名前）、仕様書の 02 用語・要件・振る舞い・受け入れ基準、仕様書 08 と Catalog の項目名・ラベルコンテキスト定義書の変更履歴
業務の流れを変えた（作業・担当・帳票・順番）作業が増減したらコンテキスト定義書 08 機能一覧と仕様書。コンテキストをまたぐ流れが変わるなら、業務フロー図の「全体」タブコンテキスト定義書の変更履歴
オブジェクトを変えた（プロパティ・操作・一覧）仕様書 06 データ項目と 08、Catalog の API 定義・テーブル定義。概念の名前や集約の境界が変わるなら、コンテキスト定義書 03 の要約コンテキスト定義書の変更履歴
機能の要件を変えたその仕様書の受け入れ基準・08 この機能の設計と、展開したテストケース。上の資料は通常そのまま仕様書の変更履歴（確定後はステータスを戻さず、履歴に残す）
この機能の設計を変えた（使う画面・API の形・テーブル・呼び出し順など）仕様書 08 と Catalog。受け入れ基準を満たし続けるかを確認する。仕様書の 01〜07 は通常そのまま仕様書の変更履歴（対象：設計）。仕様のステータスは戻さない。重要な判断は ADR
共通ルール・非機能要件の満たし方を変えた影響する仕様書の 08 と Catalog。例外として書いていた作り方が、共通ルールに吸収できないかも確認するDesign の変更履歴、ADR

AI と進めるとき

この資料の構成は「どこに何を書くか」「正本はどこか」が決まっているので、整理・下書き・整合性の確認は AI に任せられます。範囲や優先順位、仕様の確定など「決めること」は人が持ちます。うまく回すために、次の4つを決めておきます。

  1. AI へのルールを1か所に置く

    「実装の前に仕様書を読む」「正本以外に書き写さない」「決まっていないことは推測せず、未決事項として出す」「重要な技術選定は選択肢とトレードオフを出す」「承認されていない重要な設計変更はしない」などを、CLAUDE.md などの1つのファイルにまとめておきます。

  2. 人の承認点をはっきりさせる

    「仕様書のステータスを『確定』にするのは人だけ」「ADR の承認は人」と決めておくと、AI が先走りません。業務の事実（誰が何をしているか）も、人が確認します。

  3. 資料をリポジトリに置く

    「02 ディレクトリで見た全体」の構成どおりにファイルを置けば、AI が自分で読んでたどれます。HTML の雛形も読めますが、資料が増えるなら、AI が読み書きしやすい Markdown や JSON の割合を増やすと扱いやすくなります。

  4. 最初は1つのコンテキストで試す

    AI の案の質と、人の確認の負担を見てから広げます。

AI と人の分担

層AI に任せられること人が決めること
Domain業務の説明や既存資料から、ドメイン・サブドメイン・責務（RESP）の案を出す範囲（含む・含まない）、責務の優先順位
Context分割・統合の案と理由（04 の判断の順番に沿って）、用語集の下書き境界の最終決定（ADR の承認）
Model業務の聞き取り内容から、業務フロー図とオブジェクト整理の下書き業務として正しいか（業務担当の確認）
Spec01〜07 の下書き、振る舞いのケース（正常・異常・二重送信など）の洗い出し仕様の確定（業務担当の承認）
Spec 08・Catalog画面・API・テーブルの設計案と、Catalog への反映重要な技術判断の承認
Design非機能要件の満たし方の表の案、共通ルールの下書き目標値（性能・稼働率など）
確認重複・矛盾の点検、ID の対応の抜け漏れ確認直すかどうかの判断
機能を足すときの頼み方「この機能を足したい」と伝えると、AI は次を案として出せます。どのコンテキストのどの責務に当たるか（なければ責務の追加案）、業務フロー図とオブジェクトのどこが変わるか、必要な仕様書の数とそれぞれの範囲、影響する Catalog の画面・API・テーブル。人はその案を見て決めます。AI は責務やケースを網羅的に出しがちなので、最初のリリースに入れるものは人が絞ります。

関連資料

  • ドメイン定義書の雛形 ↗Domain。システムで1つ。ドメイン・サブドメインの一覧、システムの責務、コンテキストとの対応と関係。全体の業務フローへのリンク。
  • コンテキスト定義書の雛形 ↗Context。サブドメインごとに1つ。担う責務・用語・モデルと状態の要約・ルール・イベント・連携・機能一覧。
  • 業務フロー図 ↗Model ／ Flows。システムで1つのファイルに、コンテキストごとのタブと「全体」タブで業務の流れを描く。
  • オブジェクト整理 ↗Model ／ Objects。システムで1つ。オブジェクトのプロパティ・操作と、コレクション（一覧）の表示項目を整理する。
  • 機能仕様書の雛形 ↗Spec。機能ごとに1つ。実現する責務、要件・振る舞い・受け入れ基準（01〜07）と、この機能の設計（08）。
  • 画面・機能設計書 ↗Catalog ／ 画面。画面一覧と遷移、画面ごとの要素の全体（実体）。
  • デザイン要素の説明資料 ↗ · カラーコードの説明 ↗ · 画面構成と操作の考え方 ↗Design ／ 共通ルール（Frontend）。全画面に共通する色・文字・余白・部品と、画面構成・操作のルール。
  • 画面単体テストケース ↗仕様書の振る舞い・受け入れ基準から展開するテスト。
  • ADR（アーキテクチャ決定レコード）の雛形 ↗判断の理由を残す。すべての層から参照する。
