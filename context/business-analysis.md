## 01. 解決する領域

### 目的と最終ゴール

業務フローとオブジェクトモデルを、人とAIが読んで活用できる業務分析の資料として作成・管理する。最終ゴールは、その資料をもとにAIが質問・レビューで不明点を解消し、設計から実際の開発まで行えるようにすることである。

人とAIが両方の資料を参照し、業務の理解から実装へつなげる。ただし、AIによる開発は目標であり、現在のHTMLだけで実現している機能とは区別する。

### 領域と資料の位置付け

このコンテキストは、業務分析・設計のうち、業務の流れと業務の対象を整理する範囲を扱う。業務フローとオブジェクトモデルは、同じ業務を異なる角度から表す資料として扱う。

| 観点 | 位置付け |
| --- | --- |
| このコンテキストの役割 | 業務フローとオブジェクトモデルを作り、質問・レビュー・設計・開発につなげる |
| 扱う領域 | 業務分析における業務の流れと対象の整理 |
| 業務フロー | 誰が、どの情報を扱い、どの作業や受け渡しを行うかを表す |
| オブジェクトモデル | 業務の対象、属性、関係、操作、一覧の構成を表す |
| JSON・MD・HTML | 資料の保存・受け渡し・表示に用いる形式 |

`flow`と`model`は資料の種類を表す。「人とAIに読ませる資料」は資料の利用者と用途を表す。これらと、資料が扱う業務領域を区別する。

## 02. ユビキタス言語

以下をこのコンテキストの用語の定義とする。

| 用語 | このコンテキストでの意味 |
| --- | --- |
| 担当 | 情報を見る、扱う人・部署・外部の主体 |
| 作業 | 業務の中で行う行為。業務フロー上の要素 |
| 情報項目／ステータス | 業務フローの行で整理する情報や状態 |
| 帳票 | 業務で扱う帳票・外部資料 |
| 接続 | 作業の流れ、情報の受け渡し、参照、帳票とのやりとりを表す矢印 |
| オブジェクト | 業務で扱う対象。オブジェクトモデル上で属性や操作を整理する単位 |
| プロパティ | オブジェクトが持つ情報。型や参照先などを伴う |
| 操作 | オブジェクトやコレクションに対して行う行為 |
| コレクション | 1つ以上のオブジェクトから構成する一覧。表示項目と一覧・1件に対する操作を持つ |

業務フローの保存データ内の `objects` は作業・帳票を表す。オブジェクトモデルの `objects` は業務の対象を表す。同じキー名でも意味が異なる。

| 用語 | 英語名・現行コード上の対応 | 注意 |
| --- | --- | --- |
| 業務フロー | Business Flow | プログラムの実行順序とは限らない |
| 担当 | `roles` | アクセス権限とは区別する |
| 情報項目／ステータス | `rows` | 行の意味を個別に確認する |
| 作業・帳票 | `action`・`doc` | フローの `objects` の種類 |
| 接続 | `edges` | 分岐条件を含むとは限らない |
| オブジェクトモデル | Object Model | DBの物理設計とは区別する |
| オブジェクト | モデルの `objects` | フローの同名キーと区別する |
| プロパティ | `props` | DBカラムとの対応は設計時に判断する |
| 操作 | `methods`・`itemMethods` | APIと1対1とは限らない |
| コレクション | `collections` | テーブルと同一とは限らない |

### 集約の境界

未確定。現行のタブや保存単位を、そのまま整合性を保証する集約とはみなさない。

### 業務フローとオブジェクトモデルの関係

業務フローは「誰が、どの情報を扱い、何をするか」を表す。オブジェクトモデルは「扱う対象がどの情報を持ち、何ができるか」を表す。レビューと開発では、両者を照らし合わせる。

- フローの作業が、どのオブジェクトやコレクションを扱うかを確認する。
- 作業が読み取る・作成する・変更する情報を、プロパティや操作と対応付ける。
- フローの情報項目や帳票が、どの対象の情報から構成されるかを確認する。
- フローとモデルの間で、情報や操作の不足・矛盾を確認する。

例えば「経理が請求を確定する」という作業について、モデル上の「請求」の操作と、確定時に変わる状態・情報を確認する。対応は必ずしも1対1ではない。対応付けの保存方法や共通IDの仕組みは今後具体化する。

### 開発への接続

この文書は、両資料に表す業務上の意味と、その確認・活用を対象とする。他の資料の定義やシステム全体の構成は対象に含めない。

DB、API、画面、実装コード、テストは両資料から具体化する開発成果物である。業務上の条件を確認したうえで設計する。使用技術や生成・実行の仕組みは、別途決定する。

## 05. 状態とライフサイクル

資料の承認・レビュー・開発状況を管理する正式な状態と遷移は未定義である。RULE-001の情報の区別は、資料全体の承認状態とは別である。

### 想定する利用の流れ

1. 人が業務フローやオブジェクトモデルを作成し、業務の情報を整理する。
2. 人とAIが資料を読み、業務の内容について質問・回答する。
3. AIが不足・曖昧さ・矛盾をレビューし、人が業務上の判断や追加情報を示す。
4. 確認した内容を資料へ反映し、未確認事項と区別する。
5. AIが資料をもとに、画面・API・処理・テーブル定義・テストなどを具体化する。
6. AIが実装と検証を行い、人が結果を確認する。判明した業務上の変更は資料にも反映する。

これは目標とする利用の流れであり、AIとの連携方法や自動化の範囲は今後具体化する。

### 資料に必要な性質

- 人が業務の意味を理解でき、AIが対象・関係・条件を識別できる。
- 確認済みの事実、未確認事項、AIの提案・仮定を区別できる。
- レビュー指摘、設計結果、実装が、元の資料のどの要素に対応するかを追える。
- 不足する情報は確認事項として示し、AIの推測だけで業務仕様を確定しない。
- 資料の修正を次のレビューや開発に利用できる。

### 個別業務のライフサイクル

資料に描く個別業務の状態名と遷移は、その業務のコンテキストで定義する。誰がどの作業・帳票で状態を進めるかは業務フローに表す。

### 各資料を開発へつなげる際の注意

#### 業務フロー

`business_flow.html`は、担当、情報項目／ステータス、作業・帳票、接続を扱う。現在はJSON・Markdown・HTMLを出力できる。

- 矢印だけから、分岐条件、実行条件、例外処理を確定しない。
- 担当の列を、そのままシステムのアクセス権限とみなさない。
- 行は情報項目またはステータスを表すため、すべてをDBテーブルや状態へ直接変換しない。
- 開発には、必要に応じて開始・完了条件、入出力、権限、例外などを補う。

#### オブジェクトモデル

`object_model.html`は、オブジェクトの属性・型・参照・操作と、コレクションの構成を扱う。現在はJSONの保存・読み込みとテキストのコピーができる。

- オブジェクトを、そのままDBテーブルと確定しない。
- コレクションは一覧の構成を表し、テーブルではなくクエリやビューなどに対応する場合がある。
- テーブル定義には、主キー、必須・任意、一意制約、桁数、関係の多重度、削除時の扱いなどを必要に応じて補う。
- 業務フローと対応付ける際は、同じ名前であることだけで同一の対象と判断しない。

### 形式の考え方

以下の更新フローの適用範囲は、この文書が定義する業務分析コンテキストの業務フローとオブジェクトモデル、および対応するMDに限る。他のコンテキストや資料の更新方法は、それぞれの定義で扱う。このコンテキスト定義書自体はMarkdownで編集する。

更新フローは「HTML雛形作成 → ブラウザで編集 → JSON保存 → JSONをHTML内の初期データへ反映 → MD生成」とする。JSONはブラウザでの編集結果をHTMLへ戻すために使い、質問・レビューから開発までまずMDを利用する。MDだけでは必要な情報を扱えない具体的な問題が生じた場合に、開発用のJSON資料の利用を検討する（[ADR-0012](../adr/adr-0012-roundtrip-browser-edits-through-json.md)）。JSONからHTMLへの反映は現時点ではAIまたは開発者による作業であり、MD生成スクリプトの機能には含まない。

形式の選択は、必要な情報を失わず、人とAIが利用できることを優先する。トークン量は、同じ内容を対象モデルで比較して判断する。現在の業務フローのMD出力にはマトリクスと一覧の重複があるため、MDが常にJSONより小さいとは限らない。

リポジトリ内の資料更新は、JSONの編集結果をHTMLへ反映したうえで、HTMLから生成したMDを参照する。JSONをHTMLへ反映する自動化やAIへの接続方式は未確定である。技術やリポジトリ全体のルールを決める場合はADRに記録する。

### AIとの会話による手順

生成したMDをAIとの会話で渡し、対象の業務フローやオブジェクトモデルを指定して質問・レビュー・開発を依頼する。回答・指摘・採否・未確認事項は会話側で扱い、採用した変更をHTML雛形 → ブラウザ編集 → JSON保存 → HTMLへの反映 → MD生成の流れで資料へ戻す。

質問・レビューでは対象のフロー・要素ID・根拠・確認質問を示してもらい、未確認事項と提案を区別する。開発では対象MDと確認済みの条件を渡し、設計・実装・検証結果を元の要素と対応付けてもらう。利用者が結果を確認し、不足があれば会話と資料の更新に戻る。ブラウザ上のレビュー画面は作らない。
