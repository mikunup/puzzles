ARCHITECTURE DECISION RECORD

ADR-0013：Contextは実行場所を問わず責務を実現する手段全体を定義する

Contextとその機能一覧は、HTML・スクリプト・Skills・CLI・AIへの依頼手順など、このプロジェクトで責務を実現する手段全体を扱う。ブラウザ上で実行するかどうかを、一覧に含める基準にしない。

01 /

背景・課題

業務分析コンテキストの機能一覧をブラウザ機能に偏って整理したため、HTMLからMDを作成するスクリプトが抜けていた。また、ブラウザのレビュー画面を使わない方針を、AIとの会話をContextの対象から外すことと混同した。

利用者は、Contextを概念・課題を解決するための手段として捉え、スクリプト・Skillsなど、このプロジェクトでできる手段をすべて含めると指定した。

この ADR で決めることContextの責務と機能一覧に、どの実現手段を含めるか。
02 /

判断基準

  1. 責務を実現する手段を漏らさないこと：実行場所だけで機能が抜けないようにする。
  2. 何が使えるかを把握できること：実装・運用手順と未実装の案を区別する。
  3. 重複した機能を作らないこと：会話やスクリプトで実現できるものを、ブラウザ機能として作り直す前提にしない。
03 /

検討した選択肢

選択肢良い点懸念点
責務を実現する手段全体を記載（採用）手段と責務の対応を確認できる提供状況と参照先の整理が必要
ブラウザ機能のみを記載画面機能は把握しやすいスクリプト・Skills・手順が抜ける
実行場所ごとの別一覧だけで管理手段ごとには探しやすい同じ責務を全体でどう実現するか把握しにくい

選択肢ごとの詳細

責務ごとにできることと実行手段を対応付ければ、実装形態が変わってもContextの目的を追える。実行場所だけで分ける方法では、今回のような機能の記載漏れが残る。

04 /

決定

DECISION

Contextは、HTML・スクリプト・Skills・CLI・AIへの依頼手順など、責務を実現するこのプロジェクトの手段全体を定義する。機能一覧には、できること・責務・実行手段・参照先・提供状況を対応付ける。

決定の理由

利用者の指定に従い、解決する課題を軸に実現手段を把握できるようにするため。

  • ブラウザの画面だけでなく、コマンドやSkill、定義した会話手順も対象にする。
  • 実装済み・運用手順・未実装・未定義を区別する。
  • 存在しないSkillや外部AIの一般能力を、利用可能なプロジェクト機能として記載しない。
  • ブラウザのreview-dialogを再導入する決定ではない。取り下げたSPEC-0001は検討記録として維持する。
05 /

結果・影響

良い影響

  • スクリプトやSkillsも責務との対応から探せる。
  • AIとの会話で行う手順を、画面の機能と区別しながら同じContextで扱える。

受け入れる不利益

  • 機能追加時に、実行手段や提供状況も維持する必要がある。

その他の影響

AGENTS.mdに共通ルールを記録する。業務分析では、HTMLからMDを生成するスクリプト、JSONをHTMLへ反映する手順、MDを使う会話手順を機能一覧に含める。

06 /

確認と見直し

確認する指標

各責務を実現する手段と参照先を機能一覧からたどれ、未作成のSkillなどが実装済みと誤認されないこと。

見直しの条件・時期

一覧が大きくなり目的の手段を探せなくなった場合に、責務ごとの分類や参照方法を見直す。
