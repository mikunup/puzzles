ARCHITECTURE DECISION RECORD

ADR-0012：ブラウザの編集結果をJSON経由でHTMLへ反映してMDを生成する

業務フローとオブジェクトモデルは「HTML雛形作成 → ブラウザで編集 → JSON保存 → JSONをHTMLへ反映 → MD生成」の順で更新する。JSONは編集結果の受け渡しに使い、AIへの質問・レビュー・開発にはまずMDを使う。

01 /

背景・課題

ADR-0011は開発用のJSON資料を後回しにする方針だったが、ブラウザでの編集結果をHTMLファイルへ戻す経路が明確でなかった。ブラウザ内の保存だけではHTMLファイルは更新されず、そのままMDを生成しても編集結果が含まれない。利用者がJSON保存を経由する更新順序を指定した。

制約・前提

  • 現行のHTMLにはブラウザ内保存とJSON出力がある。
  • MD生成スクリプトはHTML内の初期データを読み、ブラウザ内保存は読まない。
  • 現行スクリプトはJSONからHTMLへの反映を自動化していない。
この ADR で決めることブラウザで修正した業務モデルを、リポジトリのHTMLとMDへどの順で反映するか。
02 /

判断基準

  1. 編集結果が資料に反映されること：ブラウザ内の変更を取りこぼさない。
  2. 形式ごとの役割が明確なこと：編集用の受け渡しと開発用資料を区別する。
  3. 現行の生成処理を使えること：HTMLからMDを生成する流れを継続する。
03 /

検討した選択肢

選択肢良い点懸念点
JSON保存後にHTMLへ反映してMD生成（採用）ブラウザの編集をファイルとして渡せるJSONからHTMLへの反映が必要
ブラウザ編集後にそのままHTMLからMD生成手順が少ないHTMLが未更新なら古いデータのMDになる
JSONから直接MDを生成編集結果を直接読めるHTMLを更新する今回の流れとは別の生成方式が必要

選択肢ごとの詳細

JSON保存を経由すれば、編集結果をAIまたは開発者へ渡してHTMLに反映できる。他の選択肢ではHTMLの更新が欠けるか、現行と異なる生成方式を追加する必要がある。

04 /

決定

DECISION

業務モデルは、HTMLで雛形を作成し、ブラウザで編集し、JSONへ保存する。そのJSONをHTML内の初期データへ反映してから、対応するMDを生成する。このADRでADR-0011を置き換える。

更新の順序と役割

  1. HTML雛形：ブラウザで扱う初期モデルを用意する。
  2. ブラウザ編集：人がローカルで内容を修正する。
  3. JSON保存：対象タブまたは全タブの編集結果をファイルとして取り出す。
  4. HTML更新：AIまたは開発者がJSONを確認し、対象の初期データへ反映する。タブやデータ定義の構成を変える場合は、初期化処理とMD生成スクリプトの抽出範囲も整合させる。
  5. MD生成：node build_model_markdown.mjs を実行し、--check で更新漏れを確認する。

決定の理由

利用者が指定した流れに従い、ブラウザ内だけの変更とHTMLファイルの更新を明確に分けるため。JSONを使うことは、開発用に別のJSON資料を先に整備することを意味しない。

AIへの質問・レビュー・開発にはまずMDを使い、MDで具体的な不足が判明した場合に開発用JSON資料の利用を検討する。AIレビュー用MDは表形式を継続する。JSONからHTMLへの自動反映方式はこの決定では採用しない。

05 /

結果・影響

良い影響

  • 編集結果をJSONで渡し、HTMLとMDへ順に反映できる。
  • 画面での編集とリポジトリの資料更新を混同しにくくなる。

受け入れる不利益

  • 現時点ではJSONからHTMLへの反映をAIまたは開発者が行う必要がある。
  • ブラウザ内の既存保存データが初期データより優先される場合があり、画面表示だけではHTML更新を確認できない。
  • オブジェクトモデルの生成MDのIDは文書用であり、ブラウザのIDとは異なる。

その他の影響

ADR-0010のHTMLからMDへの生成は継続する。AGENTS.md・README・Context・Specの更新手順を揃える。

06 /

確認と見直し

確認する指標

JSONで取り出した変更がHTMLの初期データと生成MDの両方に含まれ、タブ・型・参照関係が失われていないこと。

見直しの条件・時期

JSONからHTMLへの反映漏れや追従負担が繰り返し発生する場合は、自動反映や共通データ化を検討する。
