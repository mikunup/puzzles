HOW TO USE THE TEMPLATES

ドメイン定義書・コンテキスト定義書・機能仕様書の関係と使い方

3つの雛形は、システム全体（複数のドメインとサブドメイン）→ コンテキスト → 1つの機能、と粒度を下げながら「システムが何をするか」を記録するための組み合わせです。ドメイン定義書でシステムがまたがるドメイン・サブドメインと責務を洗い出し、コンテキスト定義書で責務をサブドメインごとに分けて解決し、機能仕様書でその責務を実現する機能を1つずつ定義します。

対象
設計資料を書く人・読む人
関係する雛形
domain.html / context.html / specs.html
01 /

3つの資料の役割

それぞれの資料は、扱う範囲（単位）と答える問いが違います。1つの資料に全部を書かず、粒度ごとに分けるのが基本です。

資料1ファイルの単位答える問い主な読者作るタイミング
ドメイン定義書
domain.html		システムで1つこのシステムは、どのドメイン・サブドメインにまたがり、どんな責務を担うか。責務をどのコンテキストで解決し、コンテキスト同士はどう関係するか事業・業務の責任者、全チームのリーダー、アーキテクト最初に1回。責務や分け方が変わったら更新
コンテキスト定義書
context.html		サブドメインごとに1つこのサブドメインを解決する領域では、どの責務を、どんな言葉・モデル・ルール・状態で実現するか。どの機能を作るかそのサブドメインの業務担当者と開発チームサブドメインが決まったら。用語・ルール・機能が増えたら更新
機能仕様書
specs.html		機能ごとに1つこの機能で、誰が、何をできるようになるか。どう振る舞えば責務を果たしたと言えるかその機能を作る開発者・テスト担当・業務担当機能を作る前。確定後は変更履歴に残す
ドメインは「問題」、コンテキストは「解決」ドメイン定義書はシステムで1つ作り、システムがまたがるドメインと、その中で解く問題（サブドメイン・責務）を書く資料です。含む順は システム ⊃ ドメイン ⊃ サブドメイン で、1つのシステムが複数のドメインにまたがることもあります。コンテキスト定義書は、1つのサブドメインをシステムでどう解決するか（用語・モデル・ルール）を書く資料です。基本は「1つのサブドメイン ＝ 1つのコンテキスト」で対応させます。分割・統合してよい場合は「04 コンテキストの分け方」を参照してください。
02 /

関係の全体図

上から下へ、1対多で枝分かれします。ドメイン定義書はシステムで1つで、その中でシステムがまたがるドメインを、さらにサブドメインに分けます。サブドメイン1つに、基本はコンテキスト定義書が1つ対応し（分割・統合する場合は 04 を参照）、そのコンテキストの中で作る機能ごとに仕様書ができます。

上から下へ：責務を分ける

ドメイン定義書で、システムがまたがるドメイン・サブドメインと「システムが担う責務」を洗い出して割り当て、コンテキスト定義書でそのサブドメインの解決のしかたを決め、仕様書で責務を実現する機能を1つずつ定義します。

下から上へ：ずれを戻す

仕様書を書いていて「この責務はどのコンテキストにもない」「この用語はコンテキスト定義書にない」と気づいたら、上の資料を直します。下の資料だけで辻褄を合わせないのが大切です。

横から：ADR で理由を残す

責務をどのサブドメインに入れたか、連携を API にしたかイベントにしたか、といった判断は ADR に記録します。3つの資料には結果だけを書き、理由は ADR へのリンクにします。

03 /

責務でつなぐ

3つの資料は、責務の ID（RESP-xxx）でつながります。1つの責務が、どの資料のどこに現れるかを例で示します。仕様書は「コンテキストの中で、責務を実現する機能」として定義します。

  1. ドメイン定義書 03 システムの責務：責務を定義する

    RESP-001「顧客からの注文を受け付け、内容を確定する」。きっかけは「顧客が注文を送信する」、結果は「確定した注文」。

  2. ドメイン定義書 04 サブドメインとコンテキスト：担うサブドメインと、解決するコンテキストを決める

    RESP-001 は「販売」ドメインの「受注」サブドメインが担い、1対1で「受注」コンテキストが解決する。受注のコンテキスト定義書は context-order.html。

  3. コンテキスト定義書（受注）01 解決する領域：責務を引き受ける

    「担う責務」の表に RESP-001 を載せ、このコンテキストでの実現のしかた（注文集約を作り、確定時に RULE-001 を検査する）を書く。

  4. コンテキスト定義書（受注）08 機能一覧：機能に分ける

    RESP-001 を実現する機能として、SPEC-0001「注文明細を変更する」と SPEC-0002「注文を確定する」を載せる。

  5. 機能仕様書（SPEC-0001）：機能を定義する

    見出しの「コンテキスト」に受注、「実現する責務」に RESP-001 を書く。要件の根拠には、受注コンテキストのルール（RULE-002）を挙げる。

抜け漏れの確認ドメイン定義書のすべての RESP が、どれか1つのコンテキストの「担う責務」に載っていること。コンテキストのすべての RESP が、「機能一覧」のどれかの仕様書で実現されていること。この2つを確認すると、作り忘れと、担当のはっきりしない機能を防げます。
04 /

コンテキストの分け方

基本は「1つのサブドメイン ＝ 1つのコンテキスト」です。サブドメインは事業として解く「問題」の分け方で、こちらで選べるものではありません。コンテキストは「解決」の分け方で、言葉・チーム・技術・整合性の都合で設計するものです。1対1から外れてよいのは、解決の側にはっきりした理由があるときだけです。

パターン1：1つのサブドメインを、複数のコンテキストに分割する

分割するサイン例分け方
同じサブドメインの中で、言葉の意味が変わる
最も強い理由		在庫サブドメインで、倉庫の「在庫」はロット・棚番を持つ物理的なもの、販売の「在庫」は引き当て可能な数倉庫在庫と販売可能在庫のコンテキストに分ける
1チームで持てない大きさ受注が大きくなり、1チームで用語・ルールを把握しきれないチーム単位で分ける。1コンテキスト＝1チームが目安
変更頻度・リリースの周期が大きく違う料金計算は週に何度も変わるが、注文の確定処理はほとんど変わらない頻繁に変わる部分を切り出す
非機能要件が大きく違う決済のカード情報だけに PCI DSS の厳しい管理が要る。セール時に商品の閲覧だけが高負荷になる規制・性能の対象の部分を隔離する
整合性の要求が違う在庫の引き当ては即時に正しい必要があるが、売上の集計は数分遅れてもよい強い整合性が要る部分と、結果整合でよい部分を分ける
一部を既製品・レガシーが担う請求のうち、請求書の発行だけを外部サービスに任せる外部の部分を別のコンテキストとして扱い、腐敗防止層をはさむ
書き込みと読み取りで、モデルが大きく違う業務の処理と、経営向けのレポート・検索参照専用のコンテキストを作る

パターン2：複数のサブドメインを、1つのコンテキストに統合する

統合するサイン例
初期で小規模、チームが1つ立ち上げ期で、受注と在庫を1チームが作っている。境界がまだ確かでないなら、早すぎる分割は避ける
いつも一緒に変わる機能を足すたびに、2つのサブドメインを必ず同時に直している
同じトランザクションで強い整合性が要る請求と入金の消し込みを、必ず同時に成功・失敗させる必要がある
汎用サブドメインを1つの製品でまかなう会計と経費精算を、1つの SaaS がまとめて担う
実は言葉の意味が同じ分けてみたら用語がほぼ共通で、変換のコストばかり増える
統合するときの注意統合は、同じドメインのサブドメイン同士に限るのが原則です。違うドメインのサブドメインをまとめると、用語・ルールを決める業務の責任者が2人になり、変更のたびに調整が必要になります。また、コンテキストを1つにまとめても、コードのモジュール・パッケージはサブドメインごとに分けておきます。チームが増えたときや、変更の周期がずれてきたときに、切り出しやすくなります。

やってはいけない分け方

エンティティ（CRUD）単位

「顧客サービス」「商品サービス」のような分け方。ルールが散らばり、どの操作も複数のサービスを呼ぶことになります。

技術のレイヤー単位

画面・API・データベースで分けても、言葉の境界にはなりません。

画面単位

画面は機能仕様書の単位であり、コンテキストの単位ではありません。

組織図だけ

言葉もモデルも同じなのに、部署が違うという理由だけで分けることです。

分け方が間違っているサイン

分けすぎのサインまとめすぎのサイン
1つの機能追加で、いつも2つのコンテキストを同時に直す用語の定義に「〜の場合は」という条件が増える
同期 API の呼び出しが、鎖のように連なる同じ概念に、場面ごとの分岐やフラグが増え続ける
分散トランザクションや、データベースの共有が必要になる複数のチームが、同じコードで頻繁にぶつかる
連携のための変換コードが、業務ロジックより多い1つの集約・モデルが巨大になり、誰も全体を説明できない

判断の順番

  1. まず1対1で置く

    ドメイン定義書 04 の「コンテキストとの対応」に、サブドメインと同じ名前のコンテキストを1つずつ置きます。

  2. 言葉の意味が割れていないかを見る

    1つのサブドメインの中で、同じ言葉が場面によって違う意味になっていれば分割します。これが最も強い理由です。

  3. チーム・変更頻度・非機能要件・整合性を見る

    1つのサブドメインの中で、これらが大きく違えば分割を検討します。

  4. まとめるべきものを見る

    いつも一緒に変わる、または強い整合性が要るサブドメイン同士は、統合を検討します。

  5. 1対1でないものは ADR に残す

    理由を ADR に書き、ドメイン定義書 04 の「1対1にしない理由」「ADR」列を埋めます。チーム構成や規模などの前提が変わったら見直します。

05 /

どこに何を書くか

同じ情報を複数の資料に書くと、更新のたびにずれます。書く場所を1つに決め、他の資料からは ID やリンクで参照します。

書きたいこと書く場所他の資料ではどうするか
システムがまたがるドメインと、業務の責任者ドメイン定義書 02 ドメイン一覧コンテキスト定義書の見出しに、属するドメイン名を書く
システムが担う責務ドメイン定義書 03 システムの責務コンテキスト定義書 01 と仕様書の見出しには RESP 番号だけを書く
サブドメインの分け方と種別、コンテキストとの対応（1対1・分割・統合）、担当チームドメイン定義書 04 サブドメインとコンテキストコンテキスト定義書の見出しに、解決するサブドメイン・対応・種別・担当チームを揃えて書く。1対1でない理由は ADR
サブドメイン同士の関係パターンドメイン定義書 05 コンテキスト間の関係コンテキスト定義書 07 連携の「関係パターン」列を揃える
同じ言葉が別の意味になる用語ドメイン定義書 06 境界をまたぐ用語各コンテキスト定義書の用語集には、自分のコンテキストでの意味だけを書く
用語の定義、使わない言い方コンテキスト定義書 02 ユビキタス言語仕様書 02 用語・前提は、定義を書き写さず参照する
概念（集約・エンティティ・値オブジェクト）コンテキスト定義書 03 ドメインモデル項目の詳細は オブジェクト整理。仕様書のデータ項目は同じ名前を使う
業務上の決まりごと（RULE-xxx）コンテキスト定義書 04 ビジネスルール仕様書の要件の「根拠」列に RULE 番号を書く
状態と遷移コンテキスト定義書 05 状態とライフサイクル仕様書の「前提」で状態名を使う。例：状態が「下書き」のとき
他のコンテキストとの API・イベントコンテキスト定義書 06 イベント・07 連携仕様書 06 データ・インターフェースは、07 に載っているものを使う
どの機能を作るかコンテキスト定義書 08 機能一覧機能ごとに仕様書を1つ作り、一覧から仕様書へリンクする
1つの機能の要件・画面の流れ・振る舞い機能仕様書 03〜05コンテキスト定義書には書かない。画面の詳細は 画面・機能設計書
完成の条件機能仕様書 07 受け入れ基準テストは 画面単体テストケース に展開する
なぜそう決めたか（選択肢と理由）ADR3つの資料には結果だけを書き、ADR へリンクする
迷ったとき「この情報が変わったら、誰が困るか」で決めます。システム全体（複数のドメイン・チーム）が困るならドメイン定義書、そのサブドメインの担当者が困るならコンテキスト定義書、その機能を作る人だけが困るなら機能仕様書です。
06 /

作る順番

新しいシステムなら上から順に、既存システムに機能を足すなら仕様書から始めて、必要なところだけ上を直します。

新しいシステムを設計するとき

  1. ドメイン定義書でドメインと責務を洗い出す

    システムにつき domain.html を1つ作り、01 概要、02 ドメイン一覧、03 システムの責務を書きます。先に、システムがまたがるドメインと業務の責任者を確認します。責務は、人が行う業務と分けて書きます。

  2. ドメインをサブドメインに分け、コンテキストを決める

    04 で、各ドメインをサブドメインに分けて責務を割り当て、まず1対1でコンテキストを置きます。そのうえで「04 コンテキストの分け方」のルールで、分割・統合が必要かを確認します。ドメイン定義書 05 で関係を粗く描きます。

  3. サブドメインごとにコンテキスト定義書を作る

    context.html を、サブドメイン1つにつき1ファイル複製します。01 で担う責務を引き受け、業務担当者と一緒に 02 用語・03 モデル・04 ルール・05 状態を書きます。

  4. 分け方や連携の判断を ADR に残す

    「なぜこの責務をこのサブドメインに入れたか」「なぜイベント連携にしたか」を adr.html に記録し、該当箇所からリンクします。

  5. 機能一覧を作り、機能ごとに仕様書を書く

    コンテキスト定義書の 08 機能一覧に機能を並べ、specs.html を機能につき1ファイル複製します。見出しにコンテキストと実現する責務を書きます。

  6. 画面設計とテストへ展開する

    仕様書の 04 操作の流れを画面・機能設計書に、05 振る舞いと 07 受け入れ基準を画面単体テストケースに展開します。

既存のシステムに機能を足すとき

  1. どのコンテキストのどの責務か決める

    足したい機能が、どのコンテキストのどの RESP を実現するかを決めます。当てはまる責務がなければ、ドメイン定義書 03 に責務を追加し、04 で担うサブドメインと解決するコンテキストを決めます。

  2. 仕様書を書き、機能一覧に載せる

    specs.html を書き、コンテキスト定義書の 08 機能一覧に追加します。新しい用語・ルール・状態が出てきたら、コンテキスト定義書の該当箇所に追記します。

07 /

用語を揃える流れ

責務と並んで、3つの資料をつなぐのが用語です。「商品」という言葉を例に、どの資料にどう現れるかを示します。

資料書き方の例役割
ドメイン定義書
05 境界をまたぐ用語		受注：「商品」＝販売単位（SKU）
在庫：「商品」＝保管単位（ロット）		同じ言葉がサブドメインをまたぐと意味が変わることを示す。連携時に変換が必要な根拠になる
コンテキスト定義書（受注）
02 ユビキタス言語		商品 ／ Product ／ 顧客が注文できる販売単位。SKU で識別する ／ 「品目」とは呼ばないそのコンテキストでの定義を1か所に置く。コード・画面・会話で同じ名前を使う
機能仕様書（明細の変更）
02 用語・前提		商品 ／ 注文できる販売単位 ／ 参照：コンテキスト定義書（受注）02定義を書き写さず参照する。入力項目・API の名前は Product・sku に揃える
ID で結びつけるドメイン定義書の責務は RESP-001・課題は SYS-001、コンテキスト定義書のルールは RULE-001、仕様書は SPEC-0001・要件は REQ-001・受け入れ基準は AC-001 のように番号を付けると、資料をまたいで「どれの話か」を指せます。
08 /

更新のルール

1つの資料を変えたら、つながっている資料のどこを見直すかを決めておきます。

変えたこと見直す資料記録する場所
ドメインを追加した（システムの範囲が広がった）ドメイン定義書 02 にドメインを、04 にサブドメインとコンテキストを追加する。05 でドメインをまたぐ連携を確認するドメイン定義書の変更履歴。範囲の判断は ADR
責務を追加・削除した担うコンテキスト定義書の 01 担う責務と 08 機能一覧。削除なら、その責務を実現していた仕様書ドメイン定義書の変更履歴
責務を別のサブドメインに移した移す前と後のコンテキスト定義書の 01・08。関係する仕様書の「コンテキスト」と 02 用語・06 データの参照先ADR に決定を残し、ドメイン定義書の版数を上げる
コンテキストを分割・統合したドメイン定義書 04 の対応表。コンテキスト定義書を分割・統合し、01 担う責務・08 機能一覧を振り分ける。関係する仕様書の「コンテキスト」を直すADR、ドメイン定義書の変更履歴
チーム構成・規模が変わった1対1でない対応の ADR を読み直し、分割・統合の理由がまだ成り立つかを確認する見直した結果を ADR に追記する。変える場合は新しい ADR
連携方式を変えた（API → イベントなど）ドメイン定義書 05、両側のコンテキスト定義書 07、利用側の仕様書 06ADR
用語の定義・ルールを変えたその用語・ルールを使う仕様書の 02 用語、要件・振る舞い・受け入れ基準コンテキスト定義書の変更履歴
機能の要件を変えたその仕様書の受け入れ基準と、展開したテストケース。上の資料は通常そのまま仕様書の変更履歴（確定後はステータスを戻さず、履歴に残す）
