01 /

この資料の使い方

画面グループごとに、確認する目的・共通の前提・ケース表をまとめています。条件を設定し、期待する画面表示と操作を確認してOK／NGを記録します。

読む順番：確認すること → 前提 → ケース名と条件 → 期待結果 → 実施結果。ケースごとの詳しい準備・操作は「準備・操作の詳細」、用語や設定値は表の下から開けます。
正常 想定する利用・状態の確認バリデーション 入力や購入条件の不成立を確認異常 通信失敗・権限拒否・競合などを確認

区分はテスト内容の分類です。バリデーションや異常でも、期待どおりに案内・操作抑止ができれば実施結果はOKです。売り切れ・非公開など、あらかじめ想定した表示状態の切り替えは正常に含めています。

テスト範囲・組み合わせの選び方

API・認証・時刻・ルーターはテスト用に差し替え、表示・入力・要求内容・遷移を確認します。残高・在庫の実更新や権限判定そのものはAPI・結合テストで確認します。

購入条件・商品編集では2条件の組み合わせを網羅するペアワイズを利用し、個々の境界値や操作手順も同じ表に収録しています。

同じ値でも操作順序が異なるケースは残しています。実施結果とメモはブラウザ内へ自動保存し、JSONにも書き出せます。設計書の実装を実行するページではありません。

実行前の準備

  1. 対象画面を1つずつ起動できるテスト環境と、要求を記録できるAPIモックを用意します。
  2. 前ケースのストア・セッション・URL・API呼び出し履歴をリセットします。全注文テストにCLOCKを適用します。
  3. ブラウザ・ビルド識別子・実施者・実施日を下の実施情報に記録します。
  4. 準備データとケースの差分を設定し、操作後のDOM・ボタン状態・遷移先・API要求回数を確認します。
境界条件の取り決めこのテスト例はnow < expiresAtを期限内、now >= expiresAtを期限切れとして扱います。期限と完全一致する場合の扱いは、実装前に設計書にも合意・反映してください。文字数のケースは「あ」の繰り返しを使い、絵文字などの数え方は別途仕様確定が必要です。
